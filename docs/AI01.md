## 🤖 Assistant

先纠正下名字：是 **`rio_readn`** 和 **`rio_writen`**（末尾的 n 表示 "n bytes"），出自 CSAPP **10.5.1 "Rio 无缓冲 I/O"**。它们是对 `read`/`write` 的**"健壮版"封装**——专门解决真实世界里 `read`/`write` 会**短读/短写**的坑。

## 一、`rio_readn`：读满 n 字节（或读到 EOF）

```c
ssize_t rio_readn(int fd, void *usrbuf, size_t n);
// 返回：实际读到的字节数（>= 0）；0 表示一开始就 EOF；-1 表示出错
```

**它做的事**：从 fd 的当前位置读，**努力凑够 n 字节**。

- 如果 `read` 一次没读够（**短读**），它**自动循环继续读**，直到：
  - 凑够 n 字节 → 返回 n；或者
  - 遇到 **EOF** → 返回真正读到的字节数（**可能小于 n**）；
  - 出错 → 返回 -1。
- 遇到 `errno == EINTR`（被信号打断）时**自动重试**，不当作错误。

**关键点**：`rio_readn` **只有在碰到 EOF 时才会返回小于 n 的值**。否则它一定帮你凑满 n。

## 二、`rio_writen`：写满 n 字节（绝不打折）

```c
ssize_t rio_writen(int fd, void *usrbuf, size_t n);
// 返回：成功则恒为 n；出错返回 -1
```

**它做的事**：从 usrbuf 写 n 字节，**一定要全写出去**。

- 如果 `write` 一次没写完（**短写**），它**自动循环**继续写，直到 n 字节全部写完；
- `EINTR` 同样自动重试；
- 出错返回 -1。

**关键点**：`rio_writen` **永远不返回短计数**——要么返回 n（全写完），要么返回 -1。

## 三、两者最本质的区别（重点）

| | `rio_readn` | `rio_writen` |
|---|---|---|
| 会不会返回短计数 | **会**（仅当遇到 EOF） | **绝不**（除非出错） |
| 为什么 | 读少了没关系，读者知道"只来了这么多"，可以再读 | 写少了**不可接受**：数据已经交出去了，你**无法知道**到底写成功多少 |
| 循环的意义 | 只是"顺手帮你凑满" | 是**必须**的，否则数据会丢 |

一句话理解：
- **读**短了是**自然发生**且**可以接受**的（尤其 EOF）；
- **写**短了是**信息丢失的风险**，所以必须循环写满。

## 四、它们到底在防什么坑

**坑 1：短读 / 短写。**
`read(fd, buf, 4096)` 完全可能只返回 100，这**不是错误**。`rio_readn` 帮你把"没读够"这件事处理掉。

**坑 2：`EINTR`。**
`read`/`write` 可能被信号打断，返回 -1 且 `errno == EINTR`。这时应该**重试**，而不是当失败。两个函数都内建了这个重试。

**注意**：它们**不解决**"一次读取会跨越缓冲区边界"的问题——`rio_readn` 只是给你"稳稳读到 n 字节"，**按行切分**不归它管（那是 10.5.2 的 `rio_readlineb`）。

## 五、和你 lrg 项目的关系

**思想层面**（这才是你要带走的）：
- 你在 lrg 里手写的读循环，本质上就是 `rio_readn` 的核心：**`while (没读够) { n = read(...); 处理短读和 EINTR }`**。理解了 `rio_readn`，你就理解了自己循环该长什么样。
- `rio_readn` 用 `while` 包裹 `read`、`EINTR` 重试——这正是自测题第 13、17 题想考的处理方式。

**实操层面**（注意分寸）：

---

**一句话总结**：`rio_readn` = 帮你**读满 n 字节**（EOF 才可能短）；`rio_writen` = 保证**写满 n 字节**（绝不短写）。两者的共同价值是**自动处理短读/短写和 `EINTR`**，这正是系统级 I/O 必须自己扛的责任。
